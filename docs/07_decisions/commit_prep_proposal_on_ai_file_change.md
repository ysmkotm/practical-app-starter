# AIがファイル変更を伴う作業を完了したときのコミット準備案提示

**Document Version** : 1.0

**更新日** : 2026/07/30

**ステータス** : 決定

---

## 1. 目的

Git 操作の実行主体は人間に限定したまま、AI がファイル変更を伴う作業を完了したときに、ステージング範囲・コミット分割・メッセージ案を終了報告として提示する運用を定め、コミット時の判断コストを下げる。

---

## 2. 背景

[`docs/07_decisions/git_operations_human_only.md`](git_operations_human_only.md) により、ステージング・コミット・プッシュ等の実行は人間、AI は説明・差分・メッセージ案の提示までに限定されている。この実行境界は今後も維持したい。

一方、実際のコミットでは次を毎回人間が考える必要があり、変更内容を最も把握している AI に提案させた方が効率的である。

- どこまでステージングするか
- 何コミットに分けるべきか
- コミットメッセージをどうするか

既存の [`docs/02_rules/git.md`](../02_rules/git.md) §7 は「メッセージ案の提示までを担当」と書いていたが、**いつ・どの粒度で提示するか**は義務化されておらず、運用として定着しにくかった。

また、作業完了時の報告に関する独立した正本はなく、[`docs/02_rules/ai.md`](../02_rules/ai.md) のチャット運用や [`docs/02_rules/development.md`](../02_rules/development.md) の区切り記述に近い内容が分散していた。Git 固有の準備内容をどこに置くかも整理が必要だった。

---

## 3. 検討した案

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 現状維持（任意のメッセージ案提示）|既存の「提示まで可」のままとする|変更コストがない|提示の有無・粒度が安定せず、人間のコミット判断コストが残る|
|B. ファイル変更完了時にコミット準備案を必須化し、正本は `git.md` §7|実行は人間のまま、準備案の項目・分割方針・簡潔さ・未コミット混在の扱いを Git ルールに定める。`ai.md` は参照のみ|実行境界を壊さない。SSOT が明確。終了報告に組み込める|毎回の終了報告が冗長になりうる（簡潔さのルールで緩和）|
|C. 「作業完了時の報告ルール」を独立ドキュメントとして新設|完了報告全般の正本を作る|報告まわりを一箇所に集められる|現状は完了報告の一般ルール需要が薄く、Git 固有内容との混在やドキュメント増加のリスクがある|
|D. AI にステージングまで任せる|準備案だけでなく `git add` 等も AI が実行|人間の手間が減る|既存の「実行は人間」方針と矛盾する|

---

## 4. 判断基準

- [`git_operations_human_only.md`](git_operations_human_only.md) の「実行は人間」を維持すること
- 同じ情報を複数ドキュメントに重複記載しないこと（SSOT）。Git 固有は `git.md`、AI の完了時行動は `ai.md` から参照
- 終了報告が冗長になりすぎないこと（構造化・短文、長文経緯との重複回避）
- 作業前からの未コミット変更と今回変更を区別できない場合でも、推測での無理な切り分けを避けられること
- [`docs/02_rules/ai.md`](../02_rules/ai.md) の協調フロー（実装 → 区切り）と自然に接続できること

---

## 5. 判断結果

**案Bを採用**する。案C・案Dは採用しない。

- Git 操作（`git add` / `git commit` / `git push` 等）の実行は従来どおり人間のみ。AI は実行しない
- AI がリポジトリ内のファイルを変更した場合は、作業完了時にコミット準備案を提示する
- 相談・調査・レビュー・設計検討のみ（ファイル変更なし）ではコミット準備案は不要
- コミット準備案の正本は [`docs/02_rules/git.md`](../02_rules/git.md) §7 とする
- [`docs/02_rules/ai.md`](../02_rules/ai.md) には完了時の行動として短く参照する（詳細は重複記載しない）
- コミット分割はファイル単位ではなく、変更の目的・責務・意味のまとまりとする（`git.md` §4 と整合）
- 提示内容は提案であり、最終判断・ステージング・コミット・push は人間が行う

コミット準備案に含める原則項目、簡潔さ、未コミット混在時の扱いは [`docs/02_rules/git.md`](../02_rules/git.md) §7 を正とする。

---

## 6. 判断理由

- 実行主体の限定と、準備案の必須化は両立できる。前者は採用判断の境界、後者は人間の判断を助ける提案である
- 案Cは「完了報告」一般の正本需要が現状薄い一方、今回の中核は Git 準備であり、`git.md` に置く方が既存の Git / AI 役割分担と整合する
- 案Dは既存判断（人間のみ実行）と矛盾するため不採用
- 冗長化リスクは「構造化・短文・本文との重複禁止」をルールに含めることで緩和できる
- 未コミット混在は区別できない場合に無理な切り分けを禁止し、確認事項へ回すことで、誤ったステージング提案を減らせる

---

## 7. 今後の対応

- 運用してみて、準備案の項目が過剰または不足であれば `git.md` §7 のみを調整する
- 終了報告の冗長さが実務上問題になる場合は、必須項目の削減を検討する
- ブランチ作成など、実行範囲に含めていない書き込み系操作は、必要性が生じた場合に [`git_operations_human_only.md`](git_operations_human_only.md) 側で見直す
