# 認知ターゲット（Version 1.0 公開向け）

**Document Version** : 1.0

**更新日** : 2026/07/30

**ステータス** : 決定（仮確定。公開後のフィードバックで見直し可）

---

## 1. 目的

Version 1.0 公開直後に **誰に見てもらうか（認知ターゲット）** を仮確定し、`README.md` の対象者・解説記事の切り口・観測の前提を揃える。

課金ターゲット（有料教材・伴走の買い手）の最終決定は対象外とする（[`public_offering_strategy.md`](public_offering_strategy.md) §5.3・§5.6、[`backlog.md`](../01_project/backlog.md) BLG-PRJ-013）。

---

## 2. 背景

- ルート [`README.md`](../../README.md) の「対象者」が広く、差別化（docs SSOT ＋ AI 協調）が誰の困りごとに刺さるかがぼやけていた
- 公開・提供方針では認知獲得の仕込みを §5.6 に置いているが、認知ターゲット自体は仮説段階だった
- Cursor で仮案を作成し、Claude Code でレビューしたうえで採用判断した（依頼文：`private/prompts/claude_review_audience.md`）

---

## 3. 検討した案

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 現行 README の広い対象者のまま|AI 学習／土台／素早い立ち上げ／業務学習を並列|門戸が広い|メッセージがぼやける。CRUD チュートリアルと同列に見られやすい|
|B. 認知ターゲットを主／副／狙わないで絞る（採用）|業務系一人〜少人数＋docs／役割分担の困りごとに寄せる|差別化と整合。記事・README が書きやすい|機会損失の可能性（公開後に観測で補正）|
|C. チームリードを README 前面に出す|副Bを対外メッセージの主軸にする|将来の課金仮説と直結しやすい|V1.0 の実装規模（CRUD 1 本・個人運用）では過大主張になりうる|

---

## 4. 判断基準

- リポジトリ実態（スタック・社員 CRUD 題材・`ai.md` の運用）と噛み合うこと
- 対外メッセージで AI を主役にしすぎないこと（業務システム／再現可能な型が先）
- Version 1.0 公開を遅らせる必須作業を増やさないこと
- 認知ターゲットと課金ターゲットを混同しないこと
- README には主読者だけを書き、内部の観測用ターゲットと分離すること

---

## 5. 判断結果

**案 B を採用する。** Claude レビュー指摘を反映した仮確定内容は次のとおり。

### 5.1 一文定義

Java / Spring Boot の基礎があり、業務系を一人〜少人数で回している開発者に、「docs を正本にした AI 協調の運用実例」を見せる。AI は使い始めているが、プロンプト頼みで進め方が再現できない人を中心に想定する。

### 5.2 主／副／狙わない

|区分|誰か|対外露出|
|---|---|---|
|主|一人〜少人数で業務系（社内・受託寄りの CRUD 系）を触る Java / Spring 開発者。AI は使い始めているが、プロンプト頼みで再現性が弱い人|`README.md` 対象者の中心|
|副A|副業・個人開発で「進め方の型」を持ちたい人（主との差：業務システムの実務経験がまだ薄い）|README に含めてよい|
|副B|小規模チームの技術リードで、AI 導入の「型」を探している人|**認知の副・内部のみ。README 本文には出さない**（Issue・記事反応で拾えたら観測。BLG-PRJ-013 の検証材料にもなりうる）|
|狙わない|プログラミング完全未経験／Spring 未経験、SPA・モダン FE だけの学習者、スター数だけ欲しい層、「社員 CRUD の完成アプリだけ欲しい」人|対象外|

### 5.3 困りごと仮説

1. AI にコードは書かせられるが、前回と同じ進め方が再現できない
2. 設計・ルール・判断理由がチャットに散らばり、次セッションで前提が崩れる
3. Spring チュートリアルはあるが、実務寄りの docs 付きの型がない
4. AI に同じチャットで丸投げし、役割分担できていない

### 5.4 前提スキル

- **必須**: Java の基本、Spring Boot の基礎（Controller / Service / 画面遷移）
- **あるとよい**: 業務画面や DB 付きアプリを一度は触った経験
- **不要（今は）**: AI エキスパートであること、大規模チーム経験

### 5.5 README への反映方針

- 対象者セクションは本判断の主・副A・困りごとに合わせて書き換える（全面書き換えはしない）
- 「Spring Boot を素早く立ち上げたい」は主役にしない（削除または格下げ）
- 副B は README に書かない
- タグライン等の語順見直しは本判断の必須範囲外（必要なら `PRG-PRJ-001` の表現レビューで別途扱う）

### 5.6 課金ターゲットとの切り分け

- 本判断は **認知ターゲット** のみ
- 課金ターゲット（個人／受託・SES／小規模リード）は公開後のフィードバックで検証する（BLG-PRJ-013）

---

## 6. 判断理由

- スタックと題材が受託・社内寄りの業務 CRUD であり、主の定義と実態が一致する
- 困りごと仮説は [`ai.md`](../02_rules/ai.md) が解こうとしている課題（共有ドキュメント・セッション再開・役割分担）と対応する
- 一文定義で業務システム／docs を先に置き、AI を補足にすると、発信・教材化メモ（対外で AI を主役にしすぎない）と整合する
- 副B を内部観測に留めることで、V1.0 の規模に対する過大主張を避けつつ、将来の検証材料は残せる
- Claude Code レビュー（総合判定：軽い修正後に採用してよい）の差分（語順・困りごと4・副B の README 非掲載）を採用した

---

## 7. 今後の対応

- [`README.md`](../../README.md) の対象者を §5.5 に従って更新する（本判断と同時実施）

- 公開後は最小 KPI（star／記事 PV／反応）と照らし、主が外れていれば見直す（BLG-PRJ-013 と接続）
- 発信チャネル選定は BLG-PRJ-012（本判断を前提に記事角度を揃える）
