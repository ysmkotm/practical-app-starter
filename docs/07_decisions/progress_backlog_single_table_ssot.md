# progress／backlog の単一表・参照ポインタ化と人間向け読み順

**Document Version** : 1.3

**更新日** : 2026/08/05

**ステータス** : 決定

---

## 1. 目的

[`progress.md`](../01_project/progress.md) と [`backlog.md`](../01_project/backlog.md) を、機能が増えても表が増えない構成にし、同じ内容を複数箇所へ書かない（SSOT）運用を固定する。Version 1.0 完成後は progress を「今の状態を追う」役割に絞る。さらに、人間が毎日開いても迷わず・疲れずに現在地と次アクションが分かるよう、章順と内容列の粒度を整える。

---

## 2. 背景

次の課題が段階的に表面化した。

1. **作業メモと完了サマリーの重複**  
   progress 作業メモに、特定 PRG（例：PRG-PRJ-001）の経緯が日付付きで蓄積され、完了サマリーと内容が重なっていた。

2. **カテゴリ別表の増殖**  
   progress・backlog が PRJ／CMN／EMP（および DEP）ごとに表を分けており、機能追加のたびに見出し＋表が増える構造だった。

3. **backlog 内容列の肥大**  
   BLG-PRJ-011 のように、背景・目的・対象・着手内容の例・完了の目安まで1セルに詰め、Obsidian 等でのプレビューレイアウトが崩れた。

4. **Version 1.0 完成後の作業全量／着手しない一覧の重複**  
   [`version1_publish_scope.md`](version1_publish_scope.md) §7 に従い progress に置いていた V1.0 作業全量と V2 以降一覧が、スコープ判断記録・§5（当時）・backlog・`project.md` §4 と実質重複した。

5. **人間向け現在地がメタ情報の後ろにある／内容列ルールの未遡及（追記）**  
   レビュー（人間の認知負荷・読み疲れ・「今日やること」の分かりやすさ）で次が指摘された。  
   - progress は現在地サマリーが、目的・記載範囲・記載ルール（メタ）より後ろにあり、毎回ルール文を読み飛ばす必要があった  
   - backlog §3 の「内容列は1〜3文」は BLG-PRJ-011 のみ適用され、BLG-CMN-015／017／019／020、BLG-PRJ-005／006 等に見出し付き長文が残っていた  
   - `today.md`／`next.md` 新設案は、手動更新による二重管理・更新漏れのリスクから **不採用**（progress の現在地サマリーが同じ役割を既に持つ）

6. **アクションと履歴の混在（追記）**  
   未完了ボードと完了履歴、V2 ポインタと V1.0 完了案内が隣接しており、「今日動かす章」と「振り返り用の章」の境界が弱かった。

## 3. 検討した案

### 3.1 作業ボード／バックログ一覧の表構成

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 未完了1表・完了1表＋スコープ列|カテゴリ見出しをやめ、`スコープ` 列で区別する|表数が固定、機能追加に強い|同一カテゴリの塊が視覚的に弱くなる|
|B. カテゴリ別表を維持|現状維持|カテゴリ単位で読みやすい|表が増殖する|
|C. 状態横断の巨大1表|未完了・完了も1表|表は最小|「今やる／履歴」の分離が弱い|

### 3.2 作業メモと PRG 完了サマリーの分担

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 作業メモは横断経緯のみ|PRG 紐づきは完了サマリーへ|重複解消|過去メモの整理コスト|
|B. 作業メモに時系列ログを残す|日付付きで積む|その場は速い|三重化し肥大しやすい|

### 3.3 backlog 内容列の粒度

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 内容列は簡潔（目的・対象中心）|作業計画詳細は progress の該当 PRG へ。未検討の【検討事項】列挙は着手時に洗い出し（YAGNI）|セル肥大防止、SSOT 明確|着手前の細目は本文から消える|
|B. backlog に作業計画まで書く|BLG 1行で完結|開くファイルが少ない|役割混線・レイアウト破綻|

### 3.4 Version 完了後の作業全量／着手しない一覧

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 詳細表を削除し参照ポインタのみ残す|V1.0 完了案内・project／backlog への案内|重複解消|旧節番号参照が一時ずれる|
|B. 完了後も全量表を維持|progress 単体で振り返れる|三重化が続く|
|C. 章ごと削除|章数が最小|「どこを見るか」が分かりにくい|

### 3.5 progress の章順と補助ファイル（追記）

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 現在地・作業ボードを先頭へ並べ替え|メタ（目的・範囲・ルール）は後ろ|毎日の読み飛ばしが減る|節番号変更に伴う参照更新が必要|
|B. 章順は維持しメタを短縮するだけ|参照番号が安定|「今どうなっているか」までの距離は残る|
|C. `today.md`／`next.md` を新設|極薄の入口|二重管理・更新漏れのリスク（本プロジェクトで既に複数回経験）|

### 3.6 アクション章と履歴章の分離（追記）

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 未完了／V2 を前半、完了／V1.0 を後半へ分離|毎日読む章と履歴を物理的に離す|スクロール・認知負荷が下がる|節番号再変更と参照更新が必要|
|B. 完了を §2.2 のまま隣接維持|参照番号の変化が小さい|履歴がアクションの直後にあり長い|

## 4. 判断基準

- 機能が増えても表の数が増えないこと
- 同じ内容を progress／backlog／decisions で重複記載しないこと
- 「今の作業」と「未決定・保留」の役割分担が崩れないこと
- Obsidian 等の Markdown プレビューで1セルが破綻しないこと
- 既存の PRG-ID／BLG-ID を変更・削除・再利用しないこと
- Version 完成後は完了スコープの全量チェック表を progress に残さないこと
- 人間が毎日開くときに、現在地と次アクションへ最短でたどり着けること（追記）
- 新しい要約ファイルを増やして更新漏れを再発させないこと（追記）
- 履歴（完了 PRG・完成済み Version）は参照できるが、日常操作の視界から外すこと（追記）

---

## 5. 判断結果

**いずれも案 A を採用**する（§3.5 の補助ファイル新設は不採用。§3.6 も案 A）。

### 単一表・作業メモ・内容列

- progress／backlog はカテゴリ別表をやめ、**未完了1表・完了1表**＋スコープ列とする
- 作業メモには特定 PRG-ID に紐づく内容を書かない。PRG 詳細は完了サマリーへ
- backlog 内容列は簡潔（1〜3文目安）。作業計画詳細は progress の該当 PRG へ。判断比較は decisions へリンク

### Version 完了後のポインタ

- V1.0 作業全量・V2 以降テーマ一覧の詳細表は削除し、**参照ポインタ**のみ残す
- スコープ正本は `version1_publish_scope.md`、ロードマップは `project.md` §4、個別後回しは backlog

### 章順（追記・現行番号）

progress の章順を次とする（アクション前半／履歴後半）。

1. 現在地サマリー  
2. 作業ボード（未完了）  
3. Version 2 以降（ポインタ）  
4. 目的  
5. 記載範囲  
6. 記載ルール  
7. 作業ボード（完了・履歴）＋完了サマリー  
8. Version 1.0（履歴・ポインタ）  
9. 関連ドキュメント  
10. 更新履歴（主要な構成変更のみ。詳細は Git）

### 内容列の遡及適用（追記）

- backlog §4.1 全行に内容列ルールを遡及適用する
- 【検討事項】等の箇条書きは、対応する判断記録・PRG が無いものは要約して削ってよい（着手時に再洗い出し）
- 対応 PRG が無い着手内容の例は progress へ移さず削除し、関連情報列のリンクで足りるものとする

---

## 6. 判断理由

- 管理したい軸は「カテゴリ」ではなく「未完了か完了か」であり、カテゴリは列で足りる
- PRG の学びの正本は完了サマリー（および decisions）に寄せた方が再開時に明確
- backlog に作業スライス詳細を持つと progress と二重化する
- V1.0 スコープの正本は `version1_publish_scope.md`、将来テーマは `project.md` §4
- 人間が一番見たいのは現在地であり、メタ情報はその後ろでよい
- 要約ファイル新設は「同じ情報を複数箇所へ書く」問題を再発させる。既存の現在地サマリーで足りる
- 未着手項目の詳細検討観点は、着手時に改めて洗い出せば足りる（YAGNI）
- 完了履歴と完成済み Version は日常の視界から離した方が、アクション章の読みやすさが保たれる

---

## 7. 今後の対応

- 単一表・作業メモ／内容列・ポインタ化・章順・内容列遡及・アクション／履歴分離は 2026/08/05 時点で反映済み
- 現行の節番号は progress §1〜§10（上記）。判断記録本文中の旧節番号表記は、判断当時の番号として読まれたい場合があるが、**運用上の正は現行 progress の番号**とする
- 新規機能追加時もカテゴリ見出し＋新表は作らずスコープ列の値を増やす
- BLG 追加時は内容列を簡潔に保つ
- 将来の Version が区切りとして完成したときも、全量表を progress に残さずスコープ判断記録＋作業ボードに寄せる
- `today.md`／`next.md` は新設しない
- progress の更新履歴は主要な構成変更のみ追記し、細かい文言修正は Git に委ねる
