# 一覧画面に DataTables（クライアントサイド）を採用する判断

**Document Version** : 1.0

**更新日** : 2026/07/30

**ステータス** : 決定

---

## 1. 目的

Version 1 における一覧画面の UI 実装方針として DataTables を採用した理由、および検索・ページング・ソートの責務分担を記録する。

---

## 2. 背景

本プロジェクトでは [`docs/01_project/project.md`](../01_project/project.md) §3 に DataTables を使用技術として定めていたが、一覧画面での具体的な利用方針（検索をサーバー側で行うか、ページングをクライアント側で行うか等）は未整備だった。

EMP001 社員一覧の画面設計を進めるにあたり、一覧画面共通の UI 方針を [`docs/02_rules/ui.md`](../02_rules/ui.md) として明文化する必要が生じた。

Version 1 は教材・スターターキットとしての理解しやすさを重視しており、過度に複雑な一覧実装は避けたい。

---

## 3. 検討した案

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. HTML テーブルのみ|サーバー側で検索・ページング・ソートを実装|依存ライブラリが少ない|UI 実装コストが高い。ページング UX の作り込みが必要|
|B. DataTables クライアントサイド + サーバー検索（採用）|検索のみサーバー側、ページング・ソートは DataTables|実装がシンプル。一覧 UX を短期間で整えやすい|検索結果全件を HTML に載せるため、件数増加時に性能面の課題が出る|
|C. DataTables サーバーサイド処理|検索・ページング・ソートをすべて Ajax 連携|大量データに強い|Version 1 の規模に対して実装・理解コストが高い|

---

## 4. 判断基準

- Version 1 のデータ規模・学習目的に見合ったシンプルさ
- 初学者が処理の流れを追いやすいこと
- 将来、大量データ対応へ移行できること
- 開発ドキュメント間で SSOT を維持できること

---

## 5. 判断結果

**案Bを採用**する。

Version 1 の一覧画面方針は以下とする。

- 一覧画面には DataTables を使用する
- ページング・ソートは DataTables のクライアントサイド機能を利用する
- 検索は DataTables 標準の全文検索は使用せず、画面上部の検索条件からサーバー側（Spring Boot / MyBatis）で実行する
- 検索は GET（クエリパラメータ）で実装する
- DataTables のサーバーサイド処理は Version 1 では採用しない
- 将来、大量データ対応が必要になった場合はサーバーサイド処理への移行を検討する

---

## 6. 判断理由

- 検索条件は業務要件に依存するためサーバー側で実行する必要がある。一方、ページング・列ソートは Version 1 のデータ規模ではクライアントサイドで十分対応できる。
- DataTables サーバーサイド処理（案C）は、Ajax API・ページング用 SQL・JavaScript 連携が増え、教材としての理解コストが高くなる。
- 案Bであれば、Controller → Service → Mapper による検索の流れを保ちつつ、一覧 UI の UX を DataTables に委ねられる。
- 共通方針は [`docs/02_rules/ui.md`](../02_rules/ui.md) §3、画面固有仕様は各画面設計書に記載することで SSOT を維持できる。

---

## 7. 今後の対応

- 一覧画面共通方針は [`docs/02_rules/ui.md`](../02_rules/ui.md) §3 を更新して管理する。
- 新規一覧画面を追加する際は、画面設計書 §5・§8 と本判断記録を参照する。
- 件数増加等により性能問題が発生した場合、DataTables サーバーサイド処理への移行を再検討し、判断記録と `ui.md` を更新する。
