# バックログの新設と配置（`docs/01_project/backlog.md`）

**Document Version** : 1.0

**更新日** : 2026/07/30

**ステータス** : 決定

---

## 1. 目的

設計・実装時の未決定事項・保留事項を、開発ドキュメントのどこで管理するかを決め、SSOT の観点で他ドキュメント（機能一覧・判断記録・プロジェクト概要）との役割分担を明確にする。

---

## 2. 背景

社員管理（EMP）の Controller 見直し後、詳細・登録・編集画面向けの保留事項を整理する必要があった。

当初、[`docs/03_system/features.md`](../03_system/features.md) §5 に「社員管理（EMP）の未決定事項」を追記していたが、機能一覧は **システムにどのような機能があるか・その状態を俯瞰する** ドキュメントであり、設計上の保留事項や実装メモを載せる役割とは異なる。

また、以下のドキュメントとも境界の整理が必要だった。

- [`docs/01_project/project.md`](../01_project/project.md) §4 — Version 単位の中長期ロードマップ
- [`docs/07_decisions/`](../07_decisions/) — 決定済みの判断とその理由
- [`docs/03_system/screens.md`](../03_system/screens.md) — 画面の実装状態の俯瞰

未決定事項を一覧で追跡し、判断完了後も履歴として残す仕組みが、プロジェクト全体で不足していた。

---

## 3. 検討した案

### 管理ドキュメントの候補

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. `features.md` に継続して記載|機能一覧の章として未決定事項を保持|追加コストが小さい|機能の俯瞰と保留事項が混在し、更新頻度・粒度が異なる|
|B. `docs/01_project/backlog.md` を新設|プロジェクト参入層にバックログを1ファイルで置く|入口カテゴリと整合。1ファイルで運用開始しやすい|`project.md`・`setup.md` とドキュメント種別が異なる|
|C. `docs/03_system/backlog.md` を新設|システム全体設計カテゴリに置く|機能・画面一覧と近い|未決定事項は製品構成の俯瞰ではなく、設計プロセスの管理に近い|
|D. `docs/08_backlog/` を新規カテゴリ化|独立フォルダでバックログを管理|将来のファイル分割に備えやすい|現時点は項目が少なく、番号追加・リンク修正のコストが大きい|

### 配置フォルダの候補（案 B 採用後の詳細）

|案|概要|メリット|デメリット|
|---|---|---|---|
|B-1. `01_project/backlog.md`（単一ファイル）|現行構成|`docs/README.md` の入口カテゴリと一致。判断記録より前の「未決定」層として自然|CMN と PRJ の粒度差はセクション見出しで吸収|
|B-2. `01_project/backlog/` サブフォルダ|運用ルールと一覧をファイル分割|ファイルが増えたときに整理しやすい|現状1ファイルで足りる規模では過剰|
|D. `08_backlog/` トップレベル新設|カテゴリとして独立|`06_api` と独立した置き場|番号が判断記録の後になり意味的に不自然。項目数に対してコストが高い|

---

## 4. 判断基準

- SSOT — 同じ情報を複数ドキュメントに書かないこと
- 役割の明確さ — 機能俯瞰・決定済み判断・中長期ロードマップと混同しないこと
- 新規参入者・AI が未決定事項へたどり着きやすいこと
- 現プロジェクト規模（バックログ1ファイル・十数項目程度）でのコスト対効果
- 既存の `docs` 番号体系（`01_project` → … → `07_decisions`）との整合

---

## 5. 判断結果

次を採用する。

- **未決定・保留事項の正本**として [`docs/01_project/backlog.md`](../01_project/backlog.md) を新設する
- **配置**は `docs/01_project/backlog.md` の **単一ファイル** とする（案 B + B-1）
- [`docs/03_system/features.md`](../03_system/features.md) から未決定事項の章は **削除**し、備考または関連ドキュメントから backlog へリンクするのみとする
- backlog 内の項目は **ID**（`BLG-{PRJ\|CMN\|機能ID}-{連番}`）と **状態**（未検討・検討中・保留・完了）で管理する
- **§4.1（未完了）** に未検討・検討中・保留を置く。**§4.2（完了・履歴）** には完了のみを移動する（行は原則削除しない）。保留を完了と混ぜると「まだ残っているのに履歴側へ消えた」ように見えるため、[`review_findings.md`](../01_project/review_findings.md) と同様に未完了側へ残す
- 独立カテゴリ `08_backlog/` の新設は **見送る**（案 D は採用しない）

> **追記（2026/07/30）**：当初は「完了・保留を §4.2 へ移動」としていたが、保留は今後の検討対象であるため §4.1 に残す運用へ改める（上記）。

---

## 6. 判断理由

- 未決定事項は「機能の有無・状態」とは別次元の情報であり、`features.md` に置くと一覧の役割が曖昧になる
- `07_decisions` は決定済み（または検討の詳細）の記録であり、未着手の保留一覧を置く場所としては重い
- `project.md` §4 は中長期ロードマップであり、EMP002 実装前に判断すべき具体項目を逐次管理するには粒度が粗い
- `01_project` は `docs/README.md` で「プロジェクト参入の入口」として位置づけられており、未決定事項の確認タイミング（設計・実装着手前）と一致する
- 項目数・ファイル数が少ない現段階では、トップレベルカテゴリ追加より `01_project` 内1ファイルの方が、リンク修正コストと運用負荷が低い
- `03_system` は索引・俯瞰（機能・画面・テーブル）を主とする層（[`system_overview_folder.md`](system_overview_folder.md)）であり、ライフサイクル管理の backlog と混在させない方がよい

---

## 7. 今後の対応

- 新しい未決定・保留事項は [`backlog.md`](../01_project/backlog.md) §4.1 へ追加し、運用ルールは同ドキュメント §3 を正とする
- 判断が完了したら backlog の状態を「完了」に更新して §4.2 へ移し、決定内容は [`07_decisions/`](../07_decisions/) 等へ記録する（[`development.md`](../02_rules/development.md) §8 参照）
- バックログ項目が大幅に増え、§4.2 の履歴が読みにくくなった場合は、`01_project/backlog/` へのファイル分割を検討する
- それでもカテゴリとして独立が必要になった場合は、本判断記録を踏まえ、`08_backlog/` 新設を改めて判断記録に残す
- AI が backlog 追記を提案する運用は、まず docs 正本のみで試行し、不足を感じた場合のみ `.cursor/rules` へ参照1行を追加する（正本は `docs` 側を維持する）
