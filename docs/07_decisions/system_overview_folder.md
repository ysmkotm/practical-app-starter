# システム全体設計フォルダ（03_system）の追加

**Document Version** : 1.0

**更新日** : 2026/07/30

**ステータス** : 決定

---

## 1. 目的

画面設計書・テーブル定義書などの詳細設計とは別に、システム全体を俯瞰する設計ドキュメントの置き場所を決める。

---

## 2. 背景

現状は次の構成だった。

- `01_project` … プロジェクト概要
- `02_rules` … 開発ルール
- `03_screen` … 画面設計
- `04_db` … DB設計
- `05_api` … API設計
- `06_decisions` … 判断記録

画面一覧・テーブル一覧・機能一覧・ER図など、「システム全体を俯瞰する層」の置き場所がなかった。

詳細設計書はある一方、機能追加時に全体を見渡す入口が弱い、という課題があった。

---

## 3. 検討した案

### フォルダ名

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. `03_system`|システム全体設計|分かりやすい|「system」がやや広い|
|B. `03_overview`|俯瞰・一覧の意図が明確|誤解が少ない|カテゴリ名の日本語と少しズレる|
|C. `03_architecture`|構成を示す|技術者には馴染みやすい|今回の目的（機能・画面・テーブル一覧）とズレやすい|

### 番号位置

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. `03` に挿入し、後続を繰り下げ|詳細設計の前に俯瞰を置く|読み順が自然|リネーム影響がある|
|B. 末尾（例：`07_system`）に追加|番号衝突なし|変更が小さい|詳細の後に全体が来る|

### ER図の置き場所

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. DB詳細側（`05_db`）に残す|DB設計書カテゴリと一致|詳細と近い|全体俯瞰が分散する|
|B. システム全体側（`03_system`）へ移す|一覧・ERを俯瞰層に集約|全体を見やすい|DB詳細フォルダからERが外れる|

---

## 4. 判断基準

- 初見でも「全体 → 詳細」の順で読めること
- 将来の機能追加（商品管理・受注管理など）でも拡張しやすいこと
- 詳細設計書との二重管理を避けること（全体側は索引・俯瞰に寄せる）
- フォルダ名が役割を表していること

---

## 5. 判断結果

次を採用する。

- フォルダ名は **`03_system`**（カテゴリ名：システム全体設計）
- 番号は **`03` に挿入**し、後続を繰り下げる

```text
01_project
02_rules
03_system          … 新規
04_screen          … 旧 03_screen
05_db              … 旧 04_db
06_api             … 旧 05_api
07_decisions       … 旧 06_decisions
```

- 初期ドキュメントは次の3つから開始する
  - `features.md`（機能一覧）
  - `screens.md`（画面一覧）
  - `tables.md`（テーブル一覧）
- ER図は当初 `05_db` に残す案もあったが、最終的に **`03_system/er.md` へ移動**する
- `03_system` は索引・俯瞰を主とし、詳細は従来どおり画面設計書・テーブル定義書へ置く

---

## 6. 判断理由

- 全体俯瞰は、詳細設計の前に置く方が開発の流れに合う
- `system` は日本語カテゴリ「システム全体設計」と対応しやすい
- 一覧は全体側、定義書は詳細側、と分けると機能追加時に拡張しやすい
- ER図はテーブル間関係の俯瞰であり、一覧と同じ層に置いた方がシステム全体を見やすい

---

## 7. 今後の対応

- 機能・画面・テーブル追加時は、必要に応じて `03_system` の一覧も更新する
- VIEW一覧・API一覧は、対象が増えた段階で追加を検討する
- 関連する参照（`docs/README.md`、`naming.md`、`.cursor/rules/project.mdc` 等）は構成変更に合わせて更新する
