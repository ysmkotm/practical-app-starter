# Claude Codeの役割拡大（ドキュメント作成・更新の主担当化）

**Document Version** : 1.0

**更新日** : 2026/08/05

**ステータス** : 決定

---

## 1. 目的

Claude Codeの役割を、相談・レビュー・記録係の提案に留めず、設計書・開発ドキュメント（`progress.md`／`backlog.md`／画面設計書／判断記録等）の作成・更新の主担当まで拡大する。

---

## 2. 背景

[`claude_code_role_addition.md`](claude_code_role_addition.md)（2026/07/30）で「案C：相談・レビュー＋記録係のみ先行して任せる」を採用し、§7「今後の対応」で「運用して手応えが良ければ、実装や`ai.md §4.4`、`docs/README.md §4`の表なども含めて役割を拡大する」と既に明記していた。

2026-08-05、`progress.md`／`backlog.md`の構成整理（作業メモ整理・単一テーブル化・章の並べ替え等）を複数回にわたりClaude Codeが分析し、Cursorへ依頼文として渡して反映する、というやり取りを繰り返した。Claude Codeが実ファイルを読み込み深く分析したうえで依頼文を作成しているため、Cursorが依頼文を解釈して反映するという1段階を挟むことに翻訳ロスの懸念が生じた。本人からドキュメント作業の主担当をClaude Codeへ移す提案が出た。

---

## 3. 検討した案

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 現状維持|ドキュメント作業は引き続きCursorが担当し、Claude Codeは分析・依頼文作成に留める|既存フローを崩さない|Claude Codeの分析結果とCursorの反映結果の間に翻訳ロスが生じうる（本セッションで実際に発生）|
|B. ドキュメント作業を全面移行|設計書・`progress.md`・`backlog.md`・判断記録の作成・更新をClaude Codeの主担当とする|分析からファイル反映まで一貫して行え、翻訳ロスが解消する|実装との境界を明確にし続ける必要がある|
|C. 内容の種類で分担（採用）|ドキュメント作業（設計書・`progress.md`・`backlog.md`・判断記録）はClaude Code、コード実装・ビルド確認はCursor、という分担にする|「テキストの分析・執筆」と「コードの実装・ビルド」という得意分野の違いに沿っており、境界も明確|画面設計書のうち実装と強く紐づく部分は、CursorとClaude Codeの連携が別途必要になる場合がある|

---

## 4. 判断基準

- [`claude_code_role_addition.md`](claude_code_role_addition.md) §7で既に想定されていた拡大方針に沿う
- 実装（コード変更・ビルド確認）とドキュメント作成・更新は、必要なツール環境・得意分野が異なるため分けて考える
- 一度に全部を変えず、まずドキュメント作業から移行する（実装・ビルドはCursorに残す）

---

## 5. 判断結果

**案Cを採用**する。

- `docs/02_rules/ai.md §2` のCursor／Claude Codeの役割表を更新
- `ai.md §5.2`（システム開発での接点）の「対象整理・設計」「区切り」行の担当をClaude Codeに更新
- コードの実装・修正・ビルド確認は引き続きCursorが担当する

---

## 6. 判断理由

- 本セッションで、Claude Codeが実ファイルを読み込んで分析し、Cursorへ依頼文を渡して反映する、というやり取りを複数回繰り返した。分析とドキュメント反映を同じ主体で行えれば、この往復と翻訳ロスをなくせる
- コード実装・ビルド確認は、CursorのほうがIDE統合された環境的な強みがあり、Claude Code側では現状ビルド・動作確認の手段が整っていないため、当面Cursorに残す

---

## 7. 今後の対応

- 実際にClaude Codeがドキュメント作業を担当してみて、問題が出れば見直す
- コード実装との境界（画面設計書の「画面イメージ」節が実装とズレていないかの確認等）で連携が必要な場面が出てきたら、都度対応方法を検討する
