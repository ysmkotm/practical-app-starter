# 識別コード（employee_code）の論理名を「社員コード」から「社員番号」に変更

**Document Version** : 1.0

**更新日** : 2026/07/30

**ステータス** : 決定

---

## 1. 目的

`employee_code` の論理名（画面表示名）を「社員コード」から「社員番号」に変更した判断、および識別コードの論理名の決め方を `docs/02_rules/db.md` に明文化した理由を記録する。

---

## 2. 背景

`docs/05_screen/EMP001_社員一覧.md` の画面イメージ（ChatGPTが作成）では、一覧の列見出しに「社員番号」という表記が使われていた。一方、`docs/04_db/table/employee.md` の `employee_code` の論理名は「社員コード」（物理名の `_code` を直訳した名称）になっていた。

画面設計書のレビューを通じて「社員番号」「社員コード」「ID」という3つの呼び方が混在していることが判明し、どの名称に統一するかを確認した結果、「社員番号」に統一する方針となった。

単に `employee.md` の論理名を書き換えるだけでは、`department_code` など他の識別コード列でも将来同様の表記揺れが発生しうる。そのため、テーブル定義書の修正にとどまらず、識別コードの論理名をどう決めるかという考え方自体を `docs/02_rules/db.md` に追加することにした。

---

## 3. 検討した案

|案|概要|メリット|デメリット|
|---|---|---|---|
|A. 「社員コード」に統一|物理名 `_code` を直訳した論理名にする|物理名との対応が分かりやすい|実務では「社員番号」という呼び方が一般的で、画面設計書側の表記と食い違う|
|B. 「社員番号」に統一（採用）|業務で一般的に使われる名称を採用する|画面設計書との表記が揺れず、実務者にも分かりやすい|物理名（`_code`）と論理名（番号）の対応が一見分かりにくい|
|C. 統一ルールを設けず、テーブルごとに個別判断する|ルール化しない|対応コストがない|今後別のコード列でも同様の表記揺れが再発しやすい|

---

## 4. 判断基準

- 画面設計書・テーブル定義書など、開発ドキュメント間で用語が揺れないこと
- 実務で一般的に使われる呼び方であること
- 今後同様の識別コード列を追加する際に、再度悩まずに論理名を決められること

---

## 5. 判断結果

**案Bを採用**する。

- `docs/04_db/table/employee.md` の `employee_code` の論理名を「社員コード」から「社員番号」に変更する。
- `docs/02_rules/db.md` §2「識別コード」に、論理名・画面上の項目名は物理名を直訳せず業務で一般的な名称を採用する旨を追加する（例：`employee_code` は「社員番号」、`department_code` は「部署コード」）。

---

## 6. 判断理由

- 実務のシステムでは「社員コード」より「社員番号」という呼び方が一般的であり、実務者にとって分かりやすい名称を優先する [`docs/02_rules/naming.md`](../02_rules/naming.md) §1 の基本方針とも合致する。
- 一方で `department_code` の論理名は「部署コード」のまま維持する。部署については「コード」という呼び方が実務上も一般的であるため、`_code` という物理名の語尾を機械的に別の語へ変換するルールではなく、カラムごとに実務での呼称を確認して決める方針であることを、`db.md` の例示（`employee_code` → 社員番号、`department_code` → 部署コード）で明確にした。
- ルール化せずテーブル定義書だけを直すと、次に別の識別コード列を追加した際に同じ議論を繰り返すことになるため、判断基準を `db.md` に残すことにした。

---

## 7. 今後の対応

- 新しい識別コード（`_code`）列を追加する際は、論理名・画面表示名を検討する際に `docs/02_rules/db.md` §2 を確認し、実務での呼称を優先する。
- `docs/02_rules/db.md`・`docs/04_db/table/employee.md` の Document Version・更新日は、本記録作成時点ではまだ見直していない。
