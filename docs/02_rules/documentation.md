# ドキュメント記法ルール

**Document Version** : 1.1

**更新日** : 2026/07/30

---

## 1. 基本方針

本ドキュメントは、開発ドキュメントの共通記法を定めます。

- 本ドキュメントは、[`docs`](../) 配下の開発ドキュメントすべて（開発ルール・設計書・判断記録等）に適用します。
- 人間と AI の双方が理解しやすい記述を優先します。
- 同じ情報を複数箇所へ記載せず、必要に応じて本文中で関連する開発ドキュメントを参照します。
- **ドキュメントの種類ごとに書く範囲を限定**し、経緯・検討過程で本文を肥大化させません（§1.1）。
- 運用ルールの本文と判断の経緯（判断記録）を混同せず、経緯へのリンクは必要最小限とします（§9）。
- 記法ルールは本ドキュメントを正本（SSOT）とし、各設計書テンプレートでは**構成・記載方法・記載例**を定義します。

### 1.1 種類ごとの記載範囲

|種類|本文に書く|本文に原則書かない|
|---|---|---|
|開発ルール（`docs/02_rules`）|守るべきルール・手順|採用理由の長文、却下案の比較、経緯の再現|
|システム俯瞰（機能・画面・テーブル一覧等）|何があるか・入口・短い運用ルール|進捗、個別判断の経緯、テンプレート案内の羅列|
|設計書（画面・テーブル等）|仕様として守る内容|なぜそうしたかの経緯、検討ログ|
|判断記録（`docs/07_decisions`）|目的・背景・案比較・結論・理由|現行ルール／仕様の全文再掲（リンクで足りる）|
|progress / backlog|作業状態・未決定事項|仕様本文、判断理由の詳細|

- ルール系は「ルールが分かる」、設計書系は「設計が分かる」ことを優先します。
- 「なぜ」が必要なときは判断記録へ置き、ルール／設計書側には必要な結論だけを反映します。
- 更新時は、経緯の追記より、既存文の整理・統合・簡潔化を優先します（プロジェクトルールのドキュメント方針と同じ）。

## 2. ドキュメントヘッダ

各ドキュメントの先頭に、Document Version と更新日を記載します。

[`README.md`](../../README.md) の Version はアプリケーションのバージョンを指します。`docs` 配下の Document Version とは別管理です。

```markdown
**Document Version** : 1.0

**更新日** : 2026/07/07
```

### Document Version

- 初版は `1.0`
- 内容追加・改善は `1.1`、`1.2`
- 大きな変更は `2.0`

### 更新日

- `YYYY/MM/DD` 形式で統一します。
- 例：`2026/07/07`

---

## 3. 見出し

- ファイルタイトルは `#` を1つ使用します。
- 大見出し（各章）は `## 1.`、`## 2.` のように番号付きで統一します。
- 小見出しは `###`、`####` を使用します。
- セクション区切りには `---` を使用します。

---

## 4. バッククォート

文中で識別子や名称を示す場合は、バッククォート（`` ` ``）で囲みます。

リポジトリ内のファイルを指し示す場合は、§7 の Markdown リンクを使用します。

### 対象

|種類|例|
|---|---|
|フォルダ名|`docs`、`docs/02_rules`|
|ファイル名（リンク不要な場合）|`EmployeeController.java`|
|クラス名|`EmployeeController`|
|メソッド名|`findById`|
|変数名・定数名|`employeeId`|
|設定キー|`spring.datasource.url`|
|HTTPメソッド|`GET`、`POST`|
|画面・API の URL パス|`/`、`/employee`、`/employee/{employeeId}/edit`|

表のセル（画面一覧の URL 列、画面設計書のエントリポイント表など）も含め、上記はバッククォートで囲みます。

HTTPメソッドとパスを併記する場合は、`` `GET /employee/{employeeId}/edit` `` のようにまとめて囲んで構いません。

対象外の例：

- パンくず等の画面ラベル区切り（例：TOP / 社員管理 / 社員一覧）
- リポジトリ内ファイルへの参照（§7 の Markdown リンクを使用）

### 表記例

- 開発ドキュメントは `docs` 配下で管理する。
- `EmployeeController` の `list` メソッドを参照する。
- 一覧画面の URL は `/employee` とする。

コードの命名ルールそのものについては、[`docs/02_rules/naming.md`](naming.md) を参照してください。URL の命名（単数形・パス変数名）は同ドキュメント §3 を正とします。

## 5. コードブロック

実行コマンド、設定例、出力例など、複数行のコードやコマンドはコードブロックを使用します。

### コマンド

シェルコマンドは `bash` または `shell` を指定します。

```bash
./mvnw spring-boot:run
```

### 設定・コード例

言語に応じて指定します。

```yaml
spring:
  datasource:
    url: jdbc:postgresql://localhost:5432/app
```

### 出力例・ASCII図

言語指定が不要な場合は `text` を使用します。

```text
2026/07/07
```

## 6. 表

表は Markdown 形式で記載します。

|項目|内容|
|---|---|
|画面ID|EMP001|
|画面名|社員一覧|

- 見出し行の直後に区切り行（`|---|---|`）を記載します。
- リポジトリ内のファイルを指し示す場合は、§7 に従い Markdown リンクを使用します。

## 7. リンク

### リポジトリ内ファイル

Markdown 内でリポジトリ内のファイルを指し示す場合は、読み手がたどれるように **Markdown リンク** を使用します。

- リンク先は、Markdown の仕様に従い、現在のドキュメントからの相対パスを指定します。OS の絶対パス（例：`D:\...`）は使用しません。
- リンクテキストは、読み手がファイルの配置場所を把握しやすいよう、**リポジトリルートからのパス**を記載します。
- リポジトリルート直下のファイルは、ファイル名のみとします（例：`README.md`、`.gitignore`）。

#### 記載例

文中での参照：

- [`docs/02_rules/development.md`](development.md) §4 を参照してください。
- 入口として [`.cursor/rules/project.mdc`](../../.cursor/rules/project.mdc) を利用する。

表内での参照：

|ドキュメント|内容|
|---|---|
|[`docs/02_rules/ai.md`](ai.md)|AI協調開発の方針|
|[`docs/01_project/project.md`](../01_project/project.md)|プロジェクト概要|

### バッククォートとの使い分け

|用途|記法|
|---|---|
|ファイルを開くことを想定する|Markdown リンク（本セクション）|
|フォルダ名・識別子・名称のみ示す|バッククォート（§4）|

### 外部

外部サイトへのリンクは、必要に応じて URL または Markdown リンクを使用します。

## 8. ドキュメント構成

各ドキュメントは、必要に応じて以下の共通構成を採用します。

|項目|内容|詳細|
|---|---|---|
|Document Version・更新日|ドキュメントヘッダ|§2|
|タイトル・本文|ドキュメント本体|§3、各テンプレート|
|関連ドキュメント|参照すべき他の開発ドキュメントへのリンク|§9|
|更新履歴|利用者向けの主要な変更履歴|§12|

### 配置順

ドキュメント末尾の共通セクションは、次の順序で配置します。

1. 本文
2. 関連ドキュメント
3. 更新履歴

### 運用方針

- Document Version・更新日と本文は、原則としてすべてのドキュメントに記載します。
- 更新履歴は、必要に応じて記載します。
- 入口として機能するドキュメントは、共通構成から一部を省略しても構いません。

#### 入口ドキュメント

|ドキュメント|内容|
|---|---|
|[`README.md`](../../README.md)|プロジェクト案内（アプリ Version）|
|[`docs/README.md`](../README.md)|開発ドキュメント索引|

## 9. 関連ドキュメントの記載

各ドキュメントは、必要に応じて関連する開発ドキュメントへのリンクを記載します。

### 運用方針

- 内容を重複して記載せず、参照先へのリンクを記載します（SSOT）。
- 本文中で既に参照している場合は、重複して記載しなくても構いません。
- 表形式で「ドキュメント」「内容」の2列を記載します。
- 関連するドキュメントがない場合は、本節自体を省略して構いません。
- 判断記録では、既存の運用（§7 今後の対応の下に `### 関連ドキュメント` を配置）に従います。

### 判断記録へのリンク

運用ルール・仕様・一覧の本文では、**守るべき内容を先に書き**、判断の経緯へのリンクは次の方針とします。

|置き場|判断記録へのリンク|
|---|---|
|判断記録・backlog の完了／保留行|記載する（履歴・正本）|
|progress（進捗管理）など作業管理|方針の入口として必要なとき **1 本**|
|機能・画面・テーブル一覧の備考や関連ドキュメント|原則載せない。運用ルール本文だけで足りる|
|画面設計書・テーブル定義書など|その判断が当該仕様の理解に効くときだけ（迷いやすい例外）|

- 判断記録側の関連ドキュメントから、影響する設計書・一覧へリンクする方向を優先します。
- テンプレート・個別判断・progress / backlog を、俯瞰一覧の関連ドキュメントへ機械的に増やしません。

### 記載例

```markdown
## X. 関連ドキュメント

|ドキュメント|内容|
|---|---|
|[`docs/02_rules/db.md`](../02_rules/db.md)|DB設計ルール|
```

## 10. テンプレートとの関係

設計書ごとの**構成・記載方法・記載例**は、各テンプレートを正とします。

|種類|テンプレート|
|---|---|
|テーブル定義書|[`docs/04_db/table/_template.md`](../04_db/table/_template.md)|
|VIEW定義書|[`docs/04_db/view/_template.md`](../04_db/view/_template.md)|
|画面設計書|[`docs/05_screen/_template.md`](../05_screen/_template.md)|
|判断記録|[`docs/07_decisions/_template.md`](../07_decisions/_template.md)|

API設計書のテンプレートは、最初の API を設計する時点で整備します（[`docs/06_api/README.md`](../06_api/README.md)）。

共通記法は本ドキュメント、設計の考え方は関連する設計ルールを参照してください。記録種別・公開／非公開・価値判定は [`docs/02_rules/recording.md`](recording.md) を参照してください。

### 役割分担の目安

- すべての開発ドキュメントに共通する Markdown の書き方 → 本ドキュメントへ記載する
- 複数の設計書・DDL・実装に共通する方針 → 設計ルールへ記載する
- その設計書を書くときに必要な書き方・記載例 → テンプレートへ記載する
- 判断記録・AI協調ログ・発信・教材化メモの振り分け → [`recording.md`](recording.md) へ記載する

## 11. ドキュメント更新

- 内容を変更した場合は、更新日を見直します。
- Document Version の更新が必要な場合は、§2 のルールに従います。
- 画面設計書・テーブル定義書等の個別ドキュメントは、該当フォルダ（`docs/05_screen` 等）に配置します。索引である [`docs/README.md`](../README.md) の更新は不要です。
- 機能・画面・テーブルを追加した場合は、必要に応じて [`docs/03_system/`](../03_system/) の一覧も更新します。
- `docs/02_rules` に開発ルールを追加した場合は、必要に応じて関連する本文中の参照を更新します。
- 大きな設計変更やルール変更を行う場合は、関連する開発ドキュメントも合わせて見直します。詳細は [`docs/02_rules/development.md`](development.md) §4 を参照してください。

## 12. 更新履歴の記載

各ドキュメントでは、必要に応じて末尾へ更新履歴を記載します。

### 運用方針

- 更新履歴は、利用者向けの主要な変更内容を記録します。
- 細かな修正や表記揺れなどの軽微な変更は、公開の前後を問わず記載しません。
- 詳細な変更履歴は Git のコミット履歴で管理します。
- 公開前は原則として更新履歴を記載せず、初版公開時に Document Version `1.0` を追加します（未公開の変更を version history として残す必要がないためであり、軽微な変更を記載しない粒度の基準とは別の理由です）。
- 記載するか迷った場合は記載しません。
- 更新履歴は、関連ドキュメントの後ろに配置します（§8）。

### 記載例

```markdown
## 12. 更新履歴

|Document Version|日付|更新内容|
|---|---|---|
|1.1|2026/07/08|CSV入出力機能を追加|
|1.0|2026/07/07|初版公開|
```
