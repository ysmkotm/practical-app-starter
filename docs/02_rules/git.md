# Git運用ルール

**Document Version** : 1.0

**更新日** : 2026/07/30

---

## 1. 基本方針

本プロジェクトでは、Gitを利用して開発ドキュメント・ソースコードを管理します。

変更履歴を分かりやすく残すことで、後から変更理由や作業内容を確認しやすくすることを目的とします。

以下を基本方針とします。

- 変更内容は小さな単位でコミットする。
- 1つのコミットには、できるだけ1つの目的の変更だけを含める。
- ソースコード変更とドキュメント変更は、必要に応じて分けてコミットする。
- コミット前に差分を確認する。
- 不要なファイルや一時ファイルをコミットしない。
- AIが生成・修正した内容も、人間が確認したうえで人間がコミットする。
- Git は変更差分を残す。作業の現在地・保留・決定などの意味と状態は [`progress.md`](../01_project/progress.md) / [`backlog.md`](../01_project/backlog.md) / [`07_decisions/`](../07_decisions/) など docs が担う（詳細は [`docs/README.md`](../README.md) §5）。

---

## 2. 管理対象

Gitで管理する主な対象は以下とします。

- [`README.md`](../../README.md)
- `docs` 配下の開発ドキュメント
- AI開発支援用ファイル（`.cursor/rules` など）
- 設定ファイル
- ソースコード
- SQL・DDL
- 開発に必要な補助ファイル

以下は原則としてGit管理対象外とします。

- ビルド成果物
- IDE固有の不要ファイル
- 一時ファイル
- ログファイル
- 個人環境に依存する設定
- パスワード・APIキーなどの機密情報

管理対象外にするファイルは [`.gitignore`](../../.gitignore) に記載します。

## 3. ブランチ運用

個人開発のため、当面はシンプルなブランチ運用とします。

### mainブランチ

`main` ブランチは、動作確認済みの安定版を管理するブランチとします。

原則として、作業途中の状態は `main` に残さないようにします。

### 作業ブランチ

機能追加・修正・ドキュメント整理を行う場合は、必要に応じて作業ブランチを作成します。

ブランチ名の例

```text
feature/employee-list
fix/employee-search
docs/update-git-rule
refactor/employee-service
```

ただし、軽微なドキュメント修正など、影響が小さい変更は `main` で直接作業しても構いません。

---

## 4. コミット単位

コミットは、後から見たときに変更内容が分かる単位で行います。

分割の軸は **ファイル単位ではなく、変更の目的・責務・意味のまとまり** とします。

良い例

- 社員一覧画面の画面設計書を追加
- 社員検索条件のFormを追加
- READMEの開発環境説明を修正
- Git運用ルールを追加

避けたい例

- 複数機能の実装をまとめてコミットする
- 動作確認前の大量変更をまとめてコミットする
- 不要な整形変更と機能変更を混ぜる
- 一時ファイルを含めてコミットする
- 関連のない変更を、たまたま同じファイルに含まれるという理由だけで1コミットにまとめる

---

## 5. コミットメッセージ

コミットメッセージは、変更内容が分かる日本語で記載します。

形式は以下を基本とします。

```text
種別: 変更内容
```

種別の例

|種別|用途|
|---|---|
|add|新規追加|
|update|内容修正・改善|
|fix|不具合修正|
|refactor|動作を変えない整理|
|docs|ドキュメント修正|
|style|見た目・整形のみの修正|
|remove|削除|

例

```text
docs: Git運用ルールを追加
update: READMEの開発環境を修正
add: 社員一覧画面を追加
fix: 社員検索条件の不具合を修正
refactor: EmployeeServiceの処理を整理
```

## 6. コミット前チェック

コミット前に以下を確認します。

### 実装内容

- ソースコード変更を含む場合は、[`docs/02_rules/development.md`](development.md) §6「実装後の確認事項」を満たしていること

### Git運用

- 差分を確認したこと
- 意図しないファイルが含まれていないこと
- 機密情報が含まれていないこと

## 7. AI利用時のGit運用

CursorなどのAIを利用してコードを修正した場合も、コミット前に必ず人間が差分を確認します。

品質確認の基本方針については、[`docs/02_rules/ai.md`](ai.md) §3「品質確認の方針」を参照してください。

本セクションでは、**Git運用に固有の確認事項**と、AIがファイル変更を伴う作業を完了したときの **コミット準備案** を定めます。判断経緯は [`docs/07_decisions/commit_prep_proposal_on_ai_file_change.md`](../07_decisions/commit_prep_proposal_on_ai_file_change.md) を参照してください。

### 実行範囲

ステージング・コミット・プッシュ、およびコミットを作成・変更する操作（`revert`・`reset`・`merge`・`cherry-pick` 等）は、人間が実行します。

AIはこれらの操作自体は実行しません。変更内容の説明・差分の提示・コミット準備案（メッセージ案を含む）の提示までを担当します。

`git status`・`git diff`・`git log` などの参照系操作は対象外とし、AIが必要に応じて実行して構いません。

### コミット準備案の提示

AIがリポジトリ内のファイルを変更した場合は、作業完了時の終了報告として **コミット準備案** を提示します。

相談・調査・レビュー・設計検討のみで、リポジトリ内のファイルを変更していない場合は、コミット準備案は不要です。

コミット準備案は提案であり、最終判断・ステージング・コミット・push は人間が行います。

#### 含める内容（原則）

|項目|内容|
|---|---|
|変更ファイル一覧|今回の作業に関係する変更ファイル|
|変更内容の要約|1〜数行程度の要約（長文の作業経緯と重複させない）|
|分割方針|1コミットか複数コミットか、その理由|
|コミットごとのステージング対象|各コミットに含めるファイル（またはパス）|
|コミットメッセージ案|§5 の形式に沿った案|
|ステージング対象外|含めない方がよいファイルの有無と理由|
|コミット前の確認事項|人間が確認すべき点（意図しない差分、機密情報、動作確認の要否など）|

分割は §4 に従い、変更の目的・責務・意味のまとまりで行います。

#### 提示の簡潔さ

コミット準備案は終了報告の一部として、上記項目を構造化して短く示します。作業内容の長文説明を準備案内で繰り返さないでください。詳細な経緯が必要な場合は、準備案の外（本文）に記載します。

#### 作業前からの未コミット変更との区別

- 今回の作業による変更と、作業開始前から存在していた未コミット変更を区別できる場合は、今回の作業分を主対象とし、無関係な変更はステージング対象外候補とする。
- 区別できない場合は、その旨を明記したうえで、推測で無理に切り分けない。作業ツリー上の変更を意味のまとまりで分割案として提示し、コミット前の確認事項に「作業前からの変更の混在有無」を含める。

### 確認事項

- 依頼していないファイルが変更されていないこと
- 設計書・開発ルール・命名規則・コーディングルールに反した修正が入っていないこと
- 不要なリファクタリングが行われていないこと
- 設計書と実装内容に矛盾がないこと
- 変更理由が説明できること
- [`docs/02_rules/development.md`](development.md) §6「実装後の確認事項」を満たしていること

### 変更単位

AIが大きな変更を行った場合は、[`docs/02_rules/ai.md`](ai.md) §3.1 に従い、変更内容を小さな単位に分けて確認し、必要に応じてコミットも分けます。コミット分割の提案は、本セクションのコミット準備案として提示します。

---

## 8. プッシュ前チェック

GitHubなどのリモートリポジトリへプッシュする前に、以下を確認します。

- コミットメッセージが分かりやすいこと
- 不要なコミットが含まれていないこと
- 機密情報が含まれていないこと
- `main` ブランチへ反映して問題ない状態であること
