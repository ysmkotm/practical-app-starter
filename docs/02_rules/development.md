# 開発ルール

**Document Version** : 1.0

**更新日** : 2026/07/30

---

## 1. 基本方針

本プロジェクトでは、**設計を優先してから実装する**ことを基本方針とします。

また、本プロジェクトでは **`docs` 配下の開発ドキュメントを正本（SSOT）として管理** します。

ソースコードだけでなく、開発ドキュメントも成果物の一部と考え、継続的に改善します。

本プロジェクトでは、以下の考え方を基本とします。

- 本プロジェクトは「完成」よりも「品質」を重視する。
- シンプルで保守性・拡張性の高い実装を目指す。
- 初学者でも理解しやすい構成を意識する。
- 判断に迷った場合はシンプルな実装を優先する。

## 2. 開発活動の構成

本プロジェクトの開発は、次の **3つの領域** が重なりながら進みます。これらは独立した工程列ではありません。ChatGPT・Cursor による **AI協調** は独立した領域ではなく、3領域すべてを横断して支援する手段です。実務の中心は **① システム開発** とします。

### 2.1 3つの領域と AI 協調

|領域|内容|主な成果物・管理先|
|---|---|---|
|**① システム開発**|要件整理、設計、設計レビュー、実装、実装レビュー、テスト・動作確認|設計書、ソースコード（§3）|
|**② プロジェクト管理**|Version・完成条件、進捗、backlog、レビュー指摘索引、優先順位、機能・画面一覧（状態）、完了状況の確認|[`docs/01_project/`](../01_project/)、[`docs/03_system/`](../03_system/)（状態）|
|**③ ナレッジ管理（Knowledge Management）**|判断記録、ルール、レビュー知見の整理、振り返り、再利用可能なプロンプト|[`docs/07_decisions/`](../07_decisions/)、[`docs/02_rules/`](../02_rules/)、[`prompts/`](../../prompts/)（公開代表）、`private/`（開発正本）|

**AI協調（横断支援）** — ①〜③の各活動を ChatGPT・Cursor が支援する。詳細は [`docs/02_rules/ai.md`](ai.md) §5・§5.1。

### 2.2 活動と記録

レビューや判断整理などは **活動**（①など）として行い、結果は **記録**（②または③）として残します。活動そのものと、記録を残すドキュメントは別です。

|例|活動（領域）|記録先（領域）|
|---|---|---|
|設計レビュー|① システム開発|② [`docs/01_project/progress.md`](../01_project/progress.md)（該当 PRG の完了要約。ルール反映・保留発見があった場合。③へ昇格する場合あり）。指摘の索引は [`review_findings.md`](../01_project/review_findings.md)|
|実装レビュー|① システム開発|同上|
|作業区切り|② プロジェクト管理|② [`docs/01_project/progress.md`](../01_project/progress.md)（作業再開の起点が変わる場合）|
|設計判断の確定|① または ③|③ [`docs/07_decisions/`](../07_decisions/)（再利用価値がある場合）|
|ルール反映|③ ナレッジ管理|③ [`docs/02_rules/`](../02_rules/)|
|保留の発見|① システム開発|② [`docs/01_project/backlog.md`](../01_project/backlog.md)（本文）。索引として [`review_findings.md`](../01_project/review_findings.md) に1行|

### 2.3 運用上の原則

- 迷ったら **①（成果物を正しく作る）** を優先する。
- ②は「全部更新」ではなく、**変更規模に応じて最小限** 更新する（§3.1）。
- ③の記録（判断記録・ai_log 等）は、**再利用価値がある場合のみ** 行う。
- 設計書更新は **仕様が変わったとき** が必須（コード先行は不可）。

### 2.4 AI協調（横断支援）

本プロジェクトでは、**AIとの協調開発**を前提とします。AI協調は上記 3 領域のいずれにも関与する **支援手段** です。

- 設計書を基にコードを生成する。
- 設計変更時は、コードより先に設計書を更新する。
- AIが出力した内容は、[`docs/02_rules/ai.md`](ai.md) §3「品質確認の方針」に従い、人間が採用判断を行う。
- 開発ドキュメントは継続的に改善する。
- 最終的な判断は人間が行う。

[`.cursor/rules/project.mdc`](../../.cursor/rules/project.mdc) は Cursor にプロジェクトルールを案内するための入口として利用し、ルールの正本は `docs` 配下の開発ドキュメントとします。

ChatGPT・Cursor それぞれの役割分担、品質確認、領域別の AI 接点、依頼方法については、[`docs/02_rules/ai.md`](ai.md) を参照してください。

## 3. 機能実装の流れ

本セクションでは、**① システム開発** における機能実装時の一般的な流れを示します。AI 協調での接点は [`docs/02_rules/ai.md`](ai.md) §5・§5.1、工程の省略可否は §3.1 を参照してください。

1. 仕様整理
2. DB設計
3. 画面設計
4. Form設計
5. Controller作成
6. HTML作成
7. Service作成
8. Mapper作成
9. 動作確認
10. 必要に応じて設計書を更新

レイヤーの実装順は状況に応じて前後して構いません。

ただし、**設計を優先すること**を原則とします。

### 3.1 変更規模と工程の省略

個人開発として継続可能な運用のため、変更規模に応じて工程と記録を省略できます。迷った場合は **M（Medium）** として扱います。

#### 変更規模（Tier）

|Tier|例|
|---|---|
|**L（Large）**|新規機能・画面・API の追加|
|**M（Medium）**|既存機能への処理追加・拡張（例：EMP001 削除 POST の追加）|
|**S（Small）**|typo 修正、表示微調整、既存ロジックの小さなバグ修正|
|**D（Docs）**|開発ルール・設計書・progress 等のドキュメントのみの変更|

#### 工程・記録の目安

|Tier|必須|推奨|省略可|
|---|---|---|---|
|**L**|backlog 確認、設計書、PRG 登録、実装、動作確認、progress 更新|ChatGPT 設計レビュー、完了時のレビュー要約、features / screens 更新、**動作確認チェックリスト**|—|
|**M**|設計書差分（影響あり）、実装、動作確認|PRG 登録・更新、レビュー、progress 更新、**動作確認チェックリスト**（通し観点が増える・意図的保留が多いとき）|設計レビュー（差分が小さい場合）、チェックリスト（確認観点が自明なとき）|
|**S**|実装、動作確認|progress（フォーカスが変わる場合のみ）|PRG、設計書（仕様不変なら）、backlog、**動作確認チェックリスト**|
|**D**|整合性確認、該当 doc 更新|判断記録（方針変更時）|PRG、progress（作業再開に影響しない場合）、**動作確認チェックリスト**|

動作確認チェックリストは、PRG 完了判断のための作業補助である（仕様の正本ではない）。AI が下書きし人間が実施する。詳細は [`verification_checklist_and_test_assets.md`](../07_decisions/verification_checklist_and_test_assets.md)、AI 側の接点は [`ai.md`](ai.md) §5.2・§4.3。

#### レビュー要約（[`progress.md`](../01_project/progress.md) 完了 PRG）の基準

[`docs/01_project/progress.md`](../01_project/progress.md) の完了 PRG へのレビュー要約は、**ルール反映・保留（backlog）の発見・設計書修正など、後から参照する価値がある結果があった場合** に行います。問題なしの確認のみで学びが残らない場合は省略して構いません。REV-ID は用いません。指摘単位の追跡は [`review_findings.md`](../01_project/review_findings.md) に委譲し、完了要約へ主な FND-ID を任意でリンクして構いません。

#### 早見表

```
L: 設計書 → (設計レビュー) → PRG → 実装 → (レビュー) → 動作確認 → progress
M: 設計書差分 → 実装 → 動作確認 → (PRG / progress)
S: 実装 → 動作確認
D: doc 更新 → 整合性確認
```

試行運用中の項目（PRG-ID の全タスク必須化、ChatGPT チャット命名規則の厳格運用等）については、[`docs/07_decisions/development_activity_layers.md`](../07_decisions/development_activity_layers.md) §7 を参照してください。

## 4. ドキュメント管理

開発ドキュメントは `docs` 配下で管理します。

開発ドキュメントのカテゴリ構成は、[`docs/README.md`](../README.md) §2 を参照してください。

各開発ドキュメントは役割を分離し、同じ情報を複数箇所へ記載しないことを原則とします。

詳細なドキュメント管理ルールは担当ドキュメントへ記載し、本ドキュメントでは概要のみを記載します。

画面設計書・テーブル定義書等の個別ドキュメントは、該当するフォルダ内で管理します。

大きな設計変更やルール変更を行う場合は、関連するドキュメントも合わせて見直します。

Markdown の書き方・記法については、[`docs/02_rules/documentation.md`](documentation.md) を参照してください。

## 5. 実装前の確認事項

実装前に以下を確認します。

- 対象機能の目的が明確であること
- 関連する開発ドキュメント（開発ルール・設計書等）を確認していること
- 対象機能に関連する [`docs/01_project/backlog.md`](../01_project/backlog.md) の保留事項を確認していること
- 画面設計書・テーブル定義書・処理の流れが整理されていること
- 命名規則に沿っていること
- 既存機能への影響範囲を確認していること

Tier **S** の軽微修正では、影響範囲が明確な場合に backlog・設計書の確認を省略して構いません（§3.1）。

---

## 6. 実装後の確認事項

実装後に以下を確認します。

- 正常に動作すること
- 既存機能へ影響がないこと
- 入力チェックが想定どおり動作すること
- エラーメッセージが分かりやすいこと
- IDEまたはビルド結果に警告・エラーがないこと
- 不要なコード・コメントが残っていないこと
- 必要に応じて設計書を更新していること

## 7. 判断基準

判断に迷った場合は、以下を優先します。

1. シンプルで理解しやすいこと
2. 保守しやすいこと
3. 実務で採用しやすいこと
4. 初学者でも理解しやすいこと
5. 将来拡張しやすいこと

複雑な設計や実装を採用する場合は、採用理由を明確にします。

## 8. 判断記録

判断事項や迷った内容は、必要に応じて `docs/07_decisions` に記録します（**③ ナレッジ管理** の成果物）。

未決定・保留中の事項は、[`docs/01_project/backlog.md`](../01_project/backlog.md) で管理します。作業の現在地・全量・次タスクは、[`docs/01_project/progress.md`](../01_project/progress.md) で管理します。レビュー指摘の要約と処理先の索引は、[`docs/01_project/review_findings.md`](../01_project/review_findings.md) で管理します。[`docs/07_decisions/`](../07_decisions/) でステータスが検討中の判断がある場合は、原則としてバックログにも登録します。判断が完了したら、バックログの状態を「完了」に更新し §4.2 へ移動し、決定内容を判断記録へ記録します。保留にする場合は状態を「保留」に更新し §4.1 に残します（完了と混ぜない）。バックログの行は原則として削除せず、履歴として残します。レビュー由来で追跡価値がある指摘は、昇格・修正とあわせて findings へ1行登録します（詳細は [`review_findings.md`](../01_project/review_findings.md) §3、[`review_findings_escalation_criteria.md`](../07_decisions/review_findings_escalation_criteria.md)）。

記録タイミングの目安は §3.1 に従います。特に **L** や方針変更を伴う **D** では、同じ迷いを繰り返さない場合に判断記録を検討します。

記録する内容の例

- 技術選定の検討・採用理由
- 命名・プロジェクト名の検討
- ディレクトリ構成・設計方針の検討
- 設計変更の経緯
- 採用・不採用とした案、その理由

判断記録以外の記録種別（AI協調開発ログ・発信・教材化メモ）、公開／非公開の前提、価値判定、提案形式は [`docs/02_rules/recording.md`](recording.md) を正とします。運用ドキュメントから判断記録へのリンクの置き方は [`documentation.md`](documentation.md) §9 を正とします。
